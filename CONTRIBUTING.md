# Contributing to Prompt-Engineering

Thank you for considering a contribution. This repository is a learning environment, so the bar for content is not "long" but **correct, tested, and educational**.

## Ways to contribute

- **Guide improvements** — clearer explanations, better worked examples, updated provider notes. Technical claims about provider behavior must carry a review date and point to a verifiable source.
- **New techniques** — a new advanced guide, or a new pattern inside an existing guide. Must fit the module template below and the curriculum sequence in [`CURRICULUM.md`](CURRICULUM.md).
- **Labs and exercises** — adversarial and edge cases are especially welcome; see the lab gap list in [`ROADMAP.md`](ROADMAP.md).
- **Domain collections** — new prompt files inside an existing collection, following that collection's README format.
- **Bug reports and fixes** — broken links, inaccurate claims, formatting problems. Run `python scripts/validate.py` to catch link and structure issues.

## Ground rules

1. **Test prompts before submitting.** Run any prompt you contribute against at least one major model. If results vary across providers, say so in the text.
2. **No invented claims.** Never fabricate references, test results, benchmarks, or model capabilities. If you cannot verify a claim, either remove it or mark it clearly as unverified. Cite sources from [`references/references.md`](references/references.md) or add a dated, real source there.
3. **Provider-neutral language.** Write for "major chat models" and name specific providers only when the difference matters — with a verify-against-current-docs note.
4. **State the limits.** Every technique has failure modes and ceilings. A guide that oversells a technique will not be merged; see the limits sections in existing guides for the expected honesty level.
5. **No secrets, no real personal data.** Examples must use fictional scenarios and synthetic data. A leaked credential is already compromised — rotate it immediately, then fix the history.
6. **Markdown only for learning content.** PDFs in the collections are frozen snapshots generated by the maintainer; contribute to the Markdown source.

## Module template

Every guide in [Advanced Prompt Engineering Techniques](./Advanced%20Prompt%20Engineering%20Techniques/) and every lab follows this structure (section headings may be phrased to fit the material, but all roles must be present):

```markdown
# Title

One-paragraph purpose statement: what this is and who needs it.

## Before You Start          ← learning objectives + prerequisites (with links)
## When You Need This        ← the triggering situations
## The Core Pattern(s)       ← copyable worked examples with commentary
## Failure Modes             ← what goes wrong, how to recognize it, what to do
## Practice                  ← at least one concrete exercise
## Limits and Further Reading← what this technique cannot do; curated links
```

Domain collection prompt files use the lighter collection format (see any collection README). Labs use the lab format in [`labs/README.md`](labs/README.md).

## Workflow

1. Fork or branch from `main`.
2. Make one coherent change per commit (a guide, a lab, a template file).
3. Run the checks below.
4. Open a pull request describing what the change teaches or fixes and how you verified it.

```bash
# Checks before every commit
python scripts/validate.py     # link integrity + guide structure (stdlib only)
```

## Documentation conventions

- Use the exact filenames and relative links that exist; do not rename files without opening an issue first (see the filename stability decision in [`ROADMAP.md`](ROADMAP.md)).
- Terms are used consistently with [`glossary/glossary.md`](glossary/glossary.md); add new terms there when you introduce them.
- Placeholder conventions in prompt examples: `[ROLE]`, `[CONTEXT]`, `[TASK]`, `[FORMAT]`, `[CONSTRAINTS]`, `[PASTE X HERE]` — see [`templates/README.md`](templates/README.md).
- New external sources go into [`references/references.md`](references/references.md) with a review date.

## Commit style

Use a short, specific message, e.g.:

```
Add CURRICULUM.md as authoritative learning map with staged sequence
fix(labs): correct prerequisite links in lab-02
docs(injection): clarify that instruction-level defenses are insufficient
```
